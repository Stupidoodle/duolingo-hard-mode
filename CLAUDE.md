# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Toolchain: bun only

Use `bun` for every package and script command in this repo. Never invoke `npm`, `npx`, `yarn`, or `pnpm` locally.

| Task | Command |
| --- | --- |
| Install deps | `bun install` |
| Run all tests (+ coverage) | `bun run test` |
| Run a single test file | `bun run test tests/Challenge.test.js` |
| Run tests matching a name | `bun run test -- -t "handleSubmit"` |
| Lint | `bun x eslint .` |
| Production build | `bun run build` |
| Development build | `bun run build:dev` |
| Rebuild on change | `bun run watch` |
| Re-auth MCP browsers (user runs this, not Claude) | `bun run login` |

**`bun test` is not `bun run test`.** `bun test` invokes bun's own runner, which ignores `jest.config.cjs` — no jsdom environment and no `jest-chrome` globals, so ~50 of the 66 tests fail with `ReferenceError: document is not defined`. Always go through `bun run test` so jest actually runs.

`eslint.config.mjs` sets no `ignores`, so `eslint .` also lints generated `coverage/` and `dist/` output — the warnings it reports there are noise, not regressions.

`bun install` works without the `--legacy-peer-deps` flag that npm requires here. The CI workflows in `.github/workflows/` still use `npm install --legacy-peer-deps` against `package-lock.json`; `package-lock.json` remains the committed lockfile until those workflows are migrated.

## Browser automation and Duolingo login

`.mcp.json` configures two browser MCP servers — `playwright` and `chrome-devtools` — and pins each to a **repo-local, gitignored Chrome profile** via `--user-data-dir`:

- `.chrome-profiles/playwright/`
- `.chrome-profiles/devtools/`

The pinning is load-bearing. Left at its default, `@playwright/mcp` derives its profile directory from a hash of its launch config **and allocates a fresh one whenever the previous directory is still locked** — so a login could land in a directory the next launch never opens. Do not remove `--user-data-dir` from `.mcp.json`.

When a session expires, re-auth with `bun run login`, which reads `DUOLINGO_EMAIL` / `DUOLINGO_PASSWORD` from `.env` (gitignored; `.env.example` holds the keys) and logs both profiles in. It skips any profile that is still authenticated, and runs headed so a captcha or device-verification step can be solved by hand.

**Claude must not run `bun run login`** — it enters a password, which Claude is not permitted to do. Ask the user to run it themselves (`! bun run login` in the Claude Code prompt). Never read, print, or echo `.env`.

Chrome holds an exclusive lock on a profile directory, so both MCP browsers must be **fully quit** before `bun run login` works — the script detects this and names what to close. Note that playwright's `browser_close` only closes the tab; the browser process stays alive and keeps the lock. On login-form failure the script writes `login-debug-<profile>.png`. SSO (Google/Apple) sign-in is not supported — log in by hand for those.

Editing `.mcp.json` requires restarting Claude Code before the servers pick up new arguments.

`scripts/` is a **separate bun workspace** with its own `package.json` holding `playwright-core`. This is deliberate: the root `package.json` must stay in sync with `package-lock.json`, because `.github/workflows/release.yml` runs `npm ci`, which fails on a mismatch. Keep local dev tooling deps in `scripts/`, not in the root manifest.

## Loading the extension for manual testing

`bun run build` emits `dist/content.bundle.js`, `dist/popup.bundle.js`, and `dist/popup.html`. `manifest.json` at the repo root points at `dist/`, so `chrome://extensions` → Developer Mode → "Load unpacked" on the **repo root** loads the current build. `dist/` is gitignored; rebuild after pulling.

The release workflow zips `manifest.json` plus `dist/*` into an `extension/` folder — keep that layout in mind when changing output paths.

## Commit and PR conventions

- **Conventional Commits** (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`) — `standard-version` parses these to generate `CHANGELOG.md` and bump versions.
- **Atomic commits**: one logical change per commit. Split refactors from behavior changes; split unrelated files into separate commits rather than batching a session's work into one.
- **Never hand-edit the version or `CHANGELOG.md`.** `chore(release): x.y.z` commits are generated by `standard-version`, and `.github/workflows/release.yml` cuts the GitHub release from `package.json`'s version when a PR merges to `master`.
- `manifest.json` carries its own `version` field that must stay in sync with `package.json`.
- Branch naming in this repo follows `duolingo-hard-mode-<issue-number>` for issue work.
- `.github/PULL_REQUEST_TEMPLATE.md` expects: related issues, changes, testing performed, before/after screenshots, and a versioning-impact checkbox.

## Architecture

A Manifest V3 content script that rewrites Duolingo's click-the-word-bubbles challenges into a typing exercise. There is no background service worker — `src/content.js` and `src/popup.js` are the only two entry points (both bundled by webpack).

### Injection loop

`src/content.js` runs a `MutationObserver` over `document.body`. On every mutation it calls `enforceTyping()`, which:

1. Finds `div[data-test^='challenge challenge-']` — Duolingo's per-challenge container.
2. Derives the challenge type by stripping the `challenge challenge-` prefix off `data-test`.
3. Cleans up the previous `activeChallenge` if the div changed, then marks the new div with `data-extension-processed="true"` so it is handled exactly once.
4. Instantiates a challenge and calls `enforceTyping()` on it.

Because everything keys off Duolingo's `data-test` attributes, **a Duolingo DOM change is the most likely cause of a sudden breakage.** The selectors are scattered across `Challenge.js`, `WordBank.js`, and `ChoiceBank.js` rather than centralized.

### Two dispatch paths (important)

Challenge construction is deliberately split:

- **Factory path** — `ChallengeFactory.create(type, challengeDiv, eventManager)`. Types are registered at the top of `content.js` (`translate`, `tapComplete`, `listenTap`). `ChallengeFactory.register` rejects any class that does not extend `Challenge`.
- **Direct-construction path** — `gapFill`, `assist`, `select`, and `selectTranscription` bypass the factory and construct `ChallengeGapFill` directly, because it takes an extra `choiceDiv` argument (`div[aria-label="choice"][role="radiogroup"]`, which lives outside the challenge div) and **does not extend `Challenge`** — so it cannot be registered with the factory.

`completeReverseTranslation` is explicitly skipped. Adding a new challenge type means either registering a `Challenge` subclass, or extending the direct-construction branch if it needs out-of-tree DOM.

### Class responsibilities

- `Challenge` (abstract, `src/Challenge.js`) — the bulk of the logic. Creates the `<textarea data-extension="true">`, maps typed words onto word-bank buttons, handles space/backspace/enter/apostrophe, and manages focus. Subclasses override `extractElements()` and challenge-specific bits.
- `ChallengeTranslate`, `ChallengeTapComplete` — thin subclasses of `Challenge`.
- `ChallengeGapFill` — standalone; drives radio-button choices via `ChoiceBank` instead of a word bank.
- `WordBank` — LIFO pool over `button[data-test*='challenge-tap-token']`. `selectWord` pops the **last** available button for a word and pushes it onto `usedWordButtons`; `returnLastUsed` pops that stack back. Duplicate words in one sentence rely on this stack discipline — bugs about the wrong bubble being removed live here.
- `ChoiceBank` — same idea for `[data-test="challenge-choice"]` radio options.
- `ExtensionEventManager` — one global capture-phase `keydown`/`keypress`/`input` listener on `document`. It swallows events targeting `textarea[data-extension='true']` (`stopImmediatePropagation`) so Duolingo's own handlers never see them, then routes `' '`, `Backspace`, `Enter`, and `'` to the challenge registered under `textarea.dataset.challengeId`. Challenges register/unregister themselves by `challengeId` (`<type>-<Date.now()>`).
- `AccentUtils` — `normalizeText` (NFD + strip combining marks) and `getMatchingKey`, which resolves typed input to a word-bank key with or without accent sensitivity.
- `constants.js` — ~1400 lines, almost entirely verbatim copies of Duolingo's CSS custom properties in `CONSTANTS.STYLE.{ACTIVE,INACTIVE,SPAN,INPUT}`, so injected UI inherits native styling. Treat it as data, not code.

### Settings and messaging

`src/popup.js` writes `extensionEnabled`, `ignoreAccentsEnabled`, and `showOnPageControls` to `chrome.storage.sync`, then `chrome.tabs.sendMessage`s the active tab with `toggleExtension` / `toggleIgnoreAccents` / `toggleOnPageControls`. `content.js` handles those in `chrome.runtime.onMessage`.

Accent state lives on `window.ignoreAccentsEnabled` (a page global, not module state) — challenges read it at keypress time. `showOnPageControls` gates the two floating in-page buttons (`duo-hard-mode-toggle`, `duo-ignore-accents-toggle`), which are injected on load only when the setting is on.

Toggling the extension off disconnects the observer and calls `activeChallenge.cleanup()`; toggling on strips every `data-extension-processed` attribute and re-runs the observer, so already-rendered challenges get re-processed.

## Tests

Jest with `testEnvironment: "jsdom"`, `clearMocks: true`, coverage always on (`coverageProvider: "v8"`). `jest.setup.cjs` assigns `jest-chrome` onto `global`, which is what makes `chrome.storage` / `chrome.runtime` available in tests.

Tests mirror `src/` file-for-file and drive real DOM: they build Duolingo-shaped markup with `document.body.innerHTML` in `beforeEach`, then assert against it. When adding a challenge type, copy the markup fixture pattern from `tests/ChallengeTapComplete.test.js`.

`src/content.js` is the least-covered file (~39%) — its top-level side effects (observer setup, storage reads) make it awkward to test.

## Known DOM-coupling risks

- Word-bank text is read from `[data-test='challenge-tap-token-text']` and lowercased; matching is case-insensitive throughout.
- `ChoiceBank` reads `[data-test="challenge-judge-text"]` and falls back to `span[dir="ltr"]`.
- Duolingo re-renders challenge divs frequently; the `data-extension-processed` guard plus the `activeChallenge.challengeDiv` identity check are what prevent double-injection.
