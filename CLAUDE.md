# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Toolchain: bun only

Use `bun` for every package and script command in this repo. Never invoke `npm`, `npx`, `yarn`, or `pnpm` locally.

| Task | Command |
| --- | --- |
| Install deps | `bun install` |
| Run all tests (+ coverage) | `bun run test` |
| Run a single test file | `bun run test tests/Challenge.test.js` |
| Run tests matching a name | `bun run test -- -t "handleSubmit"` |
| Lint (CI fails on warnings) | `bun x eslint . --max-warnings 0` |
| Production build | `bun run build` |
| Development build | `bun run build:dev` |
| Rebuild on change | `bun run watch` |
| Re-auth MCP browsers (user runs this, not Claude) | `bun run login` |

**`bun test` is not `bun run test`.** `bun test` invokes bun's own runner, which ignores `jest.config.cjs` — no jsdom environment and no `jest-chrome` globals, so ~50 of the 66 tests fail with `ReferenceError: document is not defined`. Always go through `bun run test` so jest actually runs.


`bun.lock` is the only committed lockfile, and CI uses bun as well (`bun install --frozen-lockfile`, `bun run test`, `bun run build`, `bun audit`), on a single Node 24 job — jest and webpack still execute on Node. `package.json`'s `packageManager` pins the bun version `oven-sh/setup-bun` installs. If dependencies change, commit the updated `bun.lock`; `--frozen-lockfile` fails CI otherwise. Never regenerate it from scratch: it was migrated from the old npm lockfile to keep patched transitive versions, and a fresh resolve reintroduced 71 advisories.

## Browser automation and Duolingo login

`.mcp.json` configures two browser MCP servers — `playwright` and `chrome-devtools` — and pins each to a **repo-local, gitignored Chrome profile** via `--user-data-dir`:

- `.chrome-profiles/playwright/`
- `.chrome-profiles/devtools/`

The pinning is load-bearing. Left at its default, `@playwright/mcp` derives its profile directory from a hash of its launch config **and allocates a fresh one whenever the previous directory is still locked** — so a login could land in a directory the next launch never opens. Do not remove `--user-data-dir` from `.mcp.json`.

When a session expires, re-auth with `bun run login`, which reads `DUOLINGO_EMAIL` / `DUOLINGO_PASSWORD` from `.env` (gitignored; `.env.example` holds the keys) and logs both profiles in. It skips any profile that is still authenticated, and runs headed so a captcha or device-verification step can be solved by hand.

**Claude must not run `bun run login`** — it enters a password, which Claude is not permitted to do. Ask the user to run it themselves (`! bun run login` in the Claude Code prompt). Never read, print, or echo `.env`.

Chrome holds an exclusive lock on a profile directory, so both MCP browsers must be **fully quit** before `bun run login` works — the script detects this and names what to close. Note that playwright's `browser_close` only closes the tab; the browser process stays alive and keeps the lock. On login-form failure the script writes `login-debug-<profile>.png`. SSO (Google/Apple) sign-in is not supported — log in by hand for those.

Editing `.mcp.json` requires restarting Claude Code before the servers pick up new arguments.

`scripts/` is a **separate bun package** with its own `package.json` and lockfile holding `playwright-core`. Keep local dev tooling deps there, not in the root manifest, so they stay out of the extension's install, audit and CI.

## Loading the extension for manual testing

`bun run build` emits `dist/content.bundle.js`, `dist/popup.bundle.js`, and `dist/popup.html`. `manifest.json` at the repo root points at `dist/`, so `chrome://extensions` → Developer Mode → "Load unpacked" on the **repo root** loads the current build. `dist/` is gitignored; rebuild after pulling.

The release workflow zips `manifest.json` plus `dist/*` into an `extension/` folder — keep that layout in mind when changing output paths.

## Commit and PR conventions

- **Conventional Commits** (`feat:`, `fix:`, `chore:`, `refactor:`, `docs:`) — `standard-version` parses these to generate `CHANGELOG.md` and bump versions.
- **Atomic commits**: one logical change per commit. Split refactors from behavior changes; split unrelated files into separate commits rather than batching a session's work into one.
- **Never hand-edit the version or `CHANGELOG.md`.** `chore(release): x.y.z` commits are generated by `standard-version` (`bun x standard-version --skip.tag` on a `chore-release-x.y.z` branch), and `.github/workflows/release.yml` cuts the GitHub release from `package.json`'s version when a PR merges to `master`. It runs on every merged PR, so its failure on non-release merges ("tag already exists") is expected noise.
- **Chrome Web Store:** `release.yml` calls `publish-store.yml` (API v2). The store refuses every upload with `NOT_UPDATEABLE` while an earlier version is in review; `publish-store` then only warns, and the scheduled `store-sync.yml` (every 6 h, or dispatch it) publishes the newest GitHub release once nothing is in review. Re-publishing an existing tag: `gh workflow run publish-store.yml -f tag=vX.Y.Z`.
- The remote has a stale tag literally named `master`, so `git pull origin master` resolves to the tag. Fetch the branch explicitly: `git fetch origin refs/heads/master:refs/remotes/origin/master`.
- `manifest.json` carries its own `version` field that must stay in sync with `package.json`.
- Branch naming in this repo follows `duolingo-hard-mode-<issue-number>` for issue work.
- `.github/PULL_REQUEST_TEMPLATE.md` expects: related issues, changes, testing performed, before/after screenshots, and a versioning-impact checkbox.

## Architecture

A Manifest V3 extension that rewrites Duolingo's click-the-word-bubbles challenges into a typing exercise. Three webpack entry points: `src/content.js` (the content script, where nearly all behaviour lives), `src/popup.js` (the toolbar popup) and `src/background.js` (a service worker whose only job is swapping the toolbar icon).

### Injection loop

`src/content.js` runs a `MutationObserver` over `document.body`. On every mutation it calls `enforceTyping()`, which:

1. Finds `div[data-test^='challenge challenge-']` — Duolingo's per-challenge container.
2. Derives the challenge type by stripping the `challenge challenge-` prefix off `data-test`.
3. Cleans up the previous `activeChallenge` if the div changed.
4. Builds the challenge, calls `enforceTyping()`, and only then marks the div with `data-extension-processed="true"`.

**The ordering in step 4 is load-bearing.** Entering a lesson from inside the app is a client-side navigation, so React commits the challenge container before its word bank. Marking first meant a container caught in that state was marked while construction threw on the missing bank, and the "already processed" guard then skipped it forever — the extension appeared to work only after a page refresh. A missing bank or radiogroup must end the attempt and leave the container unmarked so the next mutation retries.

Because everything keys off Duolingo's `data-test` attributes, **a Duolingo DOM change is the most likely cause of a sudden breakage.** The selectors are scattered across `Challenge.js`, `WordBank.js`, and `ChoiceBank.js` rather than centralized.

### Three dispatch paths (important)

Challenge construction is deliberately split:

- **Factory path** — `ChallengeFactory.create(type, challengeDiv, eventManager)`. Types are registered at the top of `content.js` (`translate`, `tapComplete`, `listenTap`, and `tapCloze`/`tapClozeTable`/`tapCompleteTable`, which fill sentence or table blanks from the same word bank). `ChallengeFactory.register` rejects any class that does not extend `Challenge`.
- **Direct-construction path** — `gapFill`, `assist`, `select`, `selectTranscription`, `dialogue` and `definition` bypass the factory and construct `ChallengeGapFill` directly, because it takes an extra `choiceDiv` argument (`div[aria-label="choice"][role="radiogroup"]`, which lives outside the challenge div) and **does not extend `Challenge`** — so it cannot be registered with the factory.

- **Pairs path** — `listenMatch` and `match` (`PAIR_TYPES`) construct the standalone `ChallengeMatch`, but only once `ChallengeMatch.isPairLayout` accepts the tiles; until then `buildChallenge` returns null and the container stays unmarked.

`completeReverseTranslation` is explicitly skipped. Adding a new challenge type means either registering a `Challenge` subclass, or extending one of the direct-construction branches if it needs out-of-tree DOM or has no word bank.

Already typing natively, so deliberately left alone: `completeReverseTranslation`, `listenComplete`, `listen`, `name` (Duolingo renders its own text input). Not convertible: `speak`/`listenSpeak` (voice) and `listenIsolation`, whose choices are audio-only with no text in the DOM — mapping a typed word to one would need a page-world script reading React state.

### Class responsibilities

- `Challenge` (abstract, `src/Challenge.js`) — the bulk of the logic. Creates the `<textarea data-extension="true">`, maps typed words onto word-bank buttons, handles space/backspace/enter/apostrophe, and manages focus. Subclasses override `extractElements()` and challenge-specific bits.
- `ChallengeTranslate`, `ChallengeTapComplete` — thin subclasses of `Challenge`.
- `ChallengeGapFill` — standalone; drives radio-button choices via `ChoiceBank` instead of a word bank. Choices are compared through `comparable()` (leniency settings plus `normalizeSentence`), because `dialogue` choices are whole sentences with punctuation and French no-break spaces.
- `ChallengeMatch` — standalone; hides the answer column of a pairs challenge and makes Enter tap the hidden tile whose text was typed. Typing alone never taps: **a wrong pair costs a heart**. Duolingo shows tile selection only through the Web Animations API (no attribute, no class), so the class never infers it; it taps a prompt itself only when nothing can be selected (fresh challenge, or right after a pair locks in, seen as `aria-disabled="true"` through its own attribute observer).
- `WordBank` — LIFO pool over `button[data-test*='challenge-tap-token']`. `selectWord` pops the **last** available button for a word and pushes it onto `usedWordButtons`; `returnLastUsed` pops that stack back. Duplicate words in one sentence rely on this stack discipline — bugs about the wrong bubble being removed live here.
- `ChoiceBank` — same idea for `[data-test="challenge-choice"]` radio options.
- `ExtensionEventManager` — one global capture-phase `keydown`/`keypress`/`input` listener on `document`. It swallows events targeting `textarea[data-extension='true']` (`stopImmediatePropagation`) so Duolingo's own handlers never see them, then routes `' '`, `Backspace`, `Enter`, and `'` to the challenge registered under `textarea.dataset.challengeId`. Challenges register/unregister themselves by `challengeId` (`<type>-<Date.now()>`).
- `AccentUtils` — `normalizeText` (NFD + strip combining marks), `normalizeApostrophes`, `normalizeForMatch` and `getMatchingKey`, which resolves typed input to a word-bank key under the accent and apostrophe leniency settings. Inside `Challenge`, go through `matchKey`, which supplies both flags.
- `TokenText` — `readTokenText`, the only correct way to read a token's word. Courses that annotate their script render tokens as ruby with the reading in `<rt>` interleaved between the characters, so plain `textContent` returns `すsuしshi` for すし. Never read `[data-test='challenge-tap-token-text']` with `textContent` directly.
- `constants.js` — `CONSTANTS.STYLE.{ACTIVE,INACTIVE,SPAN,INPUT}`, applied with `element.style.cssText`. The rules reference Duolingo's own tokens (`rgb(var(--color-snow))`) and resolve from its `:root`, which is what makes the injected UI follow light and dark mode. **Do not paste `--color-*` declarations back in.** They were there originally, snapshotted from a dark-mode session, and because `cssText` makes them inline they overrode the page's theme and pinned everything to dark.

### Settings and messaging

`src/popup.js` writes `extensionEnabled`, `ignoreAccentsEnabled`, `ignoreApostrophesEnabled` and `showOnPageControls` to `chrome.storage.sync`, then `chrome.tabs.sendMessage`s the active tab with the matching `toggle*` action. `content.js` handles those in `chrome.runtime.onMessage`.

`src/background.js` watches `chrome.storage.onChanged` rather than listening for messages, so both the popup toggle and the on-page toggle drive the toolbar icon just by writing the setting. Icons live in `icons/` and are generated by `scripts/generate-icons.py`; `release.yml` copies that directory into the zip alongside `manifest.json` and `dist/`.

Leniency state lives on `window.ignoreAccentsEnabled` and `window.ignoreApostrophesEnabled` (page globals, not module state) — challenges read them at keypress time, and `content.js` seeds both from storage on load. `showOnPageControls` gates the two floating in-page buttons (`duo-hard-mode-toggle`, `duo-ignore-accents-toggle`), which are injected on load only when the setting is on.

Toggling the extension off disconnects the observer and calls `activeChallenge.cleanup()`; toggling on strips every `data-extension-processed` attribute and re-runs the observer, so already-rendered challenges get re-processed.

## Tests

Jest with `testEnvironment: "jsdom"`, `clearMocks: true`, coverage always on (`coverageProvider: "v8"`). `jest.setup.cjs` assigns `jest-chrome` onto `global`, which is what makes `chrome.storage` / `chrome.runtime` available in tests, and adds a `chrome.action` stub because `jest-chrome` predates Manifest V3 and has none.

`tests/helpers/challengeDom.js` builds the word-bank/answer-area DOM and returns the challenge plus a `clicked` spy array; prefer it over hand-rolling a fixture.

**`initGlobalKeyCapture` listeners leak between tests.** It attaches a capture-phase listener to `document` that calls `stopImmediatePropagation`, and document listeners outlive individual tests. Calling it once per test stacks listeners, and the first one swallows every later test's events — which looks exactly like a genuine failure. Either give the suite its own file and one shared manager, or re-register the challenge under the same id rather than re-initialising.

Tests mirror `src/` file-for-file and drive real DOM: they build Duolingo-shaped markup with `document.body.innerHTML` in `beforeEach`, then assert against it. When adding a challenge type, copy the markup fixture pattern from `tests/ChallengeTapComplete.test.js`.

**A test file that imports `src/content.js` must call `afterAll(stopContentScript)`** (`tests/helpers/contentScript.js`). The import starts a MutationObserver on `document.body`; without disconnecting it, jsdom's teardown fires it after the globals are gone and the run logs "Cannot log after tests are done" with a `document.querySelector` TypeError.

`src/content.js` is the least-covered file — its top-level side effects (observer setup, storage reads) make it awkward to test, though `tests/ContentSpaEntry.test.js` does drive it through the real MutationObserver by appending DOM in stages.

## Known DOM-coupling risks

- Word-bank text is read from `[data-test='challenge-tap-token-text']` and lowercased; matching is case-insensitive throughout.
- `ChoiceBank` reads `[data-test="challenge-judge-text"]` and falls back to `span[dir="ltr"]`.
- Duolingo re-renders challenge divs frequently; the `data-extension-processed` guard plus the `activeChallenge.challengeDiv` identity check are what prevent double-injection.
- Token `data-test` values carry the word as a prefix, as in `gato-challenge-tap-token`. That is why `WordBank` matches with `[data-test*='challenge-tap-token']` rather than an exact value, and why a token cannot be located by that attribute alone.
- Japanese and Chinese annotate tokens with ruby readings; always read them through `readTokenText`.
- Pair tiles are in DOM order prompt column first, answer column second. In `listenMatch` partners share a `data-test`; in `match` they do not (each tile's `data-test` is its own text). A tile holding several words moves the first word behind the marker (`sœur-challenge-tap-token une`), so never select tokens with `$=`.
- Word-bank bubbles can hold several words (`tu as`, `une sœur`); `Challenge.splitWords` regroups typed words into those keys.
- Japanese input uses an IME, where Space selects a candidate and Enter commits. `ExtensionEventManager` passes a keydown through untouched when `isComposing` is set or `keyCode` is 229, and defers live matching to `compositionend`. Do not add unconditional `preventDefault` back to those keys.
